Предыдущая реализация стала источником опыта для пересмотра требований и архитектуры. Текущее направление — **создание новой версии с нуля**, начиная разработку на Windows и сохраняя **GTK** как основу графического интерфейса, с дальнейшей проверкой на Linux.

## Подход к разработке

### Сначала требования и архитектура

До реализации определяю назначение компонента, его границы, ожидаемое поведение и способы проверки.

### Правильность должна быть проверяемой

Работающая демонстрация — промежуточный результат. Для устойчивого компонента нужны повторяемые проверки, включая ошибочные входные данные и неблагоприятные условия.

### Ошибка должна оставлять след

Диагностика, журналирование и обработка ошибок входят в архитектуру. Отказ должен давать достаточно информации для исследования причины.

### Зависимости требуют обоснования

Предпочитаю решения, устройство которых могу понять и контролировать. Каждая зависимость должна приносить конкретную пользу и иметь понятную роль в системе.

### Архитектурные решения нужно пересматривать

Вложенное время само по себе не оправдывает сохранение неудачного основания. Опыт предыдущей реализации должен помогать улучшать следующую.

### Документация объясняет причины

Документация должна описывать поведение системы и сохранять основания важных технических решений.
